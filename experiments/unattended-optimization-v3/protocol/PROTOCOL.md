**Status: corrective execution candidate, 2026-10-01 UTC; not frozen or launched.** This version requires a new realistic setup preflight, independent implementation review, validated readiness record, and immutable freeze before any of its three measured campaigns. Prior readiness and outcomes cannot satisfy those requirements. The user requested a new cohort after reviewing the earlier measurement coordination and figure design. This document specifies the prospective v3 rules; it does not assert that they are implemented or validated merely because they are written here. The actual freeze will record its timestamp and exact source/configuration bindings.

## 1. Question, treatment, and experimental unit

The question is whether a research-oriented multiagent workflow can improve the original portable C++20 range-statistics seed while maintaining the specified behavior. The treatment is the whole approved workflow: a lead intended to retain useful campaign context, dynamically delegated measurement and implementation work, evidence-based hypothesis revision, independent higher-order review, retained negative lessons, task-based completion, and immutable final assessment. The user selected no fixed campaign/reviewer wall-time or token caps. Time and cost are observed outcomes, not equalized treatment inputs.

The experimental unit is one complete campaign initialized from the same frozen original seed. A campaign may contain many hypotheses, branches, implementation revisions, workers, review rounds, tool calls, and benchmark blocks. None of those are independent agent experiments. Workload families are nested conditions in one synthetic programming task, not independent programming tasks. Separately initialized campaigns share the seed, task, host, model service, setup decisions, and evaluator; do not call them statistically independent without qualification.

This is initially a descriptive workflow study. It does not identify a causal benefit from delegation, stronger review, memory, profiling, or any other component. An alternative treatment or matched single-agent control requires a separately approved, prospectively frozen design. A no-change A/A measurement is an instrumentation control, not that comparator.

## 4. Roles and flexible research affordances

### Lead researcher / prototyper

The lead is primarily an orchestrator. It is intended to retain useful campaign context, chooses questions and hypotheses, prioritizes useful investigations, delegates substantial measurement and implementation work, reads concise reports and artifact pointers, asks follow-up questions, and decides which artifact to nominate. It may inspect code and run small diagnostic checks when useful, but it is not forced to personally perform every build, profile, repair, or test. Context retention is a design intent, not a measured context-efficiency benefit; a new context is not required for every hypothesis or code edit. Compact status and explicit bounded evidence retrieval limit routine context growth without hiding the permitted history.

The lead begins with the previous independently verified prototype, which is the frozen seed at campaign start. It requests an actual baseline measurement and profiling investigation from a measurement worker before claiming a bottleneck or proposing a measurement-grounded optimization. It may ask for further measurement whenever evidence is incomplete or surprising. The investigator can remain active for repeated follow-up on the same question.

The lead can keep or reject a hypothesis, investigate alternative explanations, split a question into competing hypotheses, merge compatible changes, revert a branch, revisit a contradicted claim with new evidence, or stop without an improvement. It does not owe a fixed number of hypotheses, positive results, submissions, or code changes. A well-supported negative finding is a valid research outcome.

### Dynamic workers

The lead can delegate measurement, performance diagnosis, implementation, correctness investigation, differential testing, experiment design, profiling interpretation, or another relevant specialty. Worker roles are tools for the current question, not a mandatory pipeline or a fixed agent count. It may use one worker repeatedly or several specialists, subject to actual infrastructure capacity and execution permissions. Parallel source edits require isolated branches/worktrees and explicit merge ownership. All arbitrary participant shell execution and native build, test, profile, memory-check, and benchmark jobs share the same enforced scheduler lease, including automatic development trajectories. Bounded structured reads and model planning do not take that execution lease (§8). No worker creates uncounted work merely by running in parallel.

Workers receive the concrete question, exact source hash, relevant earlier observations, artifact paths, technical resource limits, and expected evidence. Reports should be concise enough for the lead to use: what was tried, what happened, what remains uncertain, and pointers to raw outputs. Permitted full evidence remains addressable through explicit bounded retrieval; summarization must not erase negative runs or hide uncertainty. Workers may freely edit, compile, test, benchmark, profile, debug, and repair their assigned branch inside the approved environment and scope. Local failures do not consume a one-shot submission or disqualify the campaign.

The user-selected requested role map is: lead orchestrator `gpt-6.1-sol` / `high`; execution, measurement, and other implementation workers `gpt-6-luna` / `xhigh`; independent higher-order reviewer `gpt-6.1-sol` / `high`. Provider fallback is disabled. Exact identifiers, effort acceptance, provider-reported routing, and usage must pass authorized telemetry preflight before freeze. Stronger assistance used to design this harness is setup work and is accounted separately; it does not authorize silently changing this measured role map.

### Independent higher-order reviewer

The reviewer participates dynamically as completed hypotheses and meaningful checkpoints become available, including negative results and investigations with no nominated code. Review is not deferred into one final dump. Its context may persist for follow-up during the campaign; it starts independently of the proposing workers' conversation and does not inherit their hidden reasoning. Each review identifies the exact source hash, declared parent, falsifiable claim, lead/worker reports, and evidence pointers, and may ask for clarification.

For source promotion, the reviewer must inspect the relevant source/diff, rebuild that exact source under the official settings, rerun required correctness/resource tests, collect its own paired benchmark samples against the exact incumbent, rerun the relevant profiles or diagnostic traces, and inspect those traces. For a negative or no-code checkpoint, it must directly rerun the evidence needed to assess the central claim and inspect relevant traces; a new negative conclusion cannot be endorsed from a summary alone. Already verified properties of an unchanged exact hash may be cited with their evidence IDs, but new claims need an appropriate independent check. Merely reading a dashboard, accepting the lead's summary, or checking for a success flag is not independent review.

The official Memcheck gate covers all six configured public diagnostic families, not only the small-build case. Its `coverage_complete` field means completion of that configured suite, not complete branch or input-size coverage. The reviewer inspects candidate-specific size thresholds and materially different allocation/control-flow branches, requests supplemental larger/boundary probes when those branches require them, and records the actual coverage and any untested material concern. Reduced diagnostic cases and maximum-size correctness cases do not by themselves establish maximum-size Memcheck coverage. Supplemental checks cannot silently change the frozen campaign-wide suite or turn a known defect into a passing review.

Reviewer-generated samples and observations have their own IDs and provenance. Development review data remain development data because they guide acceptance and later work. They are not the embargoed final assessment. The reviewer may add targeted diagnostic tests from the contract; added tests, their motivating concern, and results are archived. Any new test promoted into a campaign-wide mandatory gate changes the evaluation regime and requires an explicit recorded rule, rather than silent asymmetric screening.

The reviewer can approve, request more evidence, identify a defect, or reject a nomination. It can require a factual correction or narrower claim. It cannot waive immutable correctness/resource/integrity requirements, edit or weaken the final evaluator, change the role model, quietly substitute code, or choose an attractive historical endpoint. If the reviewer supplies a concrete implementation fix, that contribution is optimization work: log its role/model/cost, send the fix through the lead, and require a fresh independent review by an uncontaminated reviewer context of the resulting hash. The preferred review mode diagnoses and requests work without becoming the author.

The reviewer may agree or disagree with the hypothesis independently of its promotion recommendation. A contradicted explanation can accompany a real verified improvement; a supported mechanism can produce insufficient benefit. Do not infer dishonesty from erroneous code, an incorrect hypothesis, a mistaken report, or a failed test. Describe the evidence, discrepancy, correction, and remaining uncertainty without attributing intent.

## 5. Hypotheses and ongoing investigation

A hypothesis record is written before the specific discriminating measurement used to evaluate it. Exploratory observations are allowed and labeled as such. The record identifies:

1. The exact baseline hash and measured bottleneck or anomaly motivating the question, with evidence IDs
2. The proposed mechanism and expected direction of change
3. The observable predictions and at least one result that would count against the claim
4. The relevant metrics, workload conditions, planned comparison, and material correctness/resource risks
5. Whether the test was specified before seeing its result or is an explicitly exploratory follow-up

The lead chooses the method appropriate to the question. It may do repeated same-hypothesis experiments, replace a broken local test, inspect full traces, repair code, and revise the claim. Revisions append a new version and explain what evidence changed. There is no token quota, one-submission rule, ban on local compilers, forced-context reset, or required positive result.

At closure, record one of `supported`, `contradicted`, or `inconclusive`, with the actual observations and limits. These labels concern the stated predictions under the tested conditions; they are not proofs of universal mechanism. A mixed result should be narrowed to its conditions or labeled inconclusive. A timeout, failed measurement, or insufficient statistical precision is not automatically a contradicted hypothesis. Record failures of implementation separately from a test of the conceptual mechanism.

## 6. Source nomination and promotion

Maintain two separate notions: exploratory working branches and the verified incumbent. Workers may explore temporarily slower, unfinished, or invalid code. Such code does not advance as the next shared prototype until the independent reviewer and mechanical gates verify it. A lead may continue a promising branch across research questions, but the declared verified baseline remains unchanged until promotion.

Nomination snapshots an exact source tree, parent/incumbent hash, build configuration, hypothesis report, and evidence manifest. A nomination is immutable. A repair creates a new source hash and a linked revision; review and test results from the old hash do not automatically transfer. There is no fixed maximum number of nominations; every attempt consumes recorded time/resources and remains visible.

Promotion requires full correctness/resource/integrity success, completed independent reviewer checks, and a complete official paired development comparison with ten temporal blocks and balanced arm order (five reference-first and five candidate-first pairs per family). Family speedup is exp(median(log(reference time / candidate time))); the portfolio is the equal-family geometric aggregate. Require portfolio speedup at least 1.03, the nominal one-sided 90% complete-block bootstrap lower bound strictly above 1, and every family speedup at least 1/1.10. Use 10,000 joint block resamples and seed 2026100302, reusing each sampled block-index vector across all families; the lower bound is the interpolated 10th percentile at index 0.1 × (10,000 − 1). The same implementation supplies native reports and owner decisions. These are operational practicality/noise screens, not a calibrated efficacy significance test or campaign-wide false-positive guarantee. Code below this gate can remain on an exploratory branch and participate in later combined hypotheses.

Neutral or slower groundwork is not promoted under this version; it can be preserved and developed on exploratory branches. No hypothesis explanation can waive the code-promotion gates.

The reviewer must independently sign the recommendation for the exact hash; the controller checks the machine-verifiable conditions and atomically advances that hash. Automatic controls have authority over ownership, immutability, technical process health, complete evidence, frozen gate results, and promotion consistency. They do not invent scientific explanations or overrule an unresolved reviewer concern. A reviewer cannot override a failed mechanical gate. Review disagreement or missing evidence means no promotion yet; the lead may investigate further.
An immutable review plan binds the exact nomination source and reference across builds and reviewer contexts. Re-nominating the identical source against the identical parent reuses its existing nomination; changing the reviewer, build, or report cannot reset the decision sample. The first complete valid official comparison in global append order for that plan/source/reference supplies the gate. Later measurements remain visible but cannot replace it because they are favorable. The selected measurement's actual build must have its required correctness/resource evidence, in addition to the current reviewer's own required reruns; a later build cannot supply missing evidence for the selected build by substitution.

Confirmed official semantic correctness or definite Memcheck errors disqualify that exact source under its nomination plan; a later passing rerun cannot erase them. Debugging and reproduction remain allowed, and an actual repaired source creates a linked nomination. Technical timeouts or infrastructure uncertainty are retained separately rather than automatically declared semantic proof. Cosmetic source changes do not justify a claim of an independent scientific attempt; record behaviorally equivalent variants and their earlier failures. Finite source-identity rules do not eliminate adaptive development selection.

## 7. Task-based completion, clocks, and process health

There is no fixed campaign/reviewer wall-time cap, token cap, token target, review allocation, required number of attempts, or required improvement count. Research and review can roam within the approved task and permissions. This is an agent-terminated open-ended workflow; do not describe its outcomes as fixed-budget efficacy or compare its costs to a capped workflow without that qualification. Three campaigns run serially from separately initialized seed workspaces. The real multiagent preflight is setup-only and is never included as a measured campaign.

The lead maintains an explicit queue of investigations and reviewer concerns. Each actionable entry names a concrete experiment or inspection, the evidence motivating it, an observable result, and how that result could change the implementation, claim, or next decision. A vague desire for more improvement is not by itself an actionable investigation. The lead may update priorities, discover new avenues, or retire an entry with evidence explaining why it is no longer decision-relevant. Retiring a claim does not delete its earlier results.

To propose normal completion, the lead submits a closure dossier containing: the exact current verified source; every registered hypothesis and its supported/contradicted/inconclusive disposition; linked factual reports and review outcomes; all unresolved uncertainties and their practical consequence; dispositions for failed/unfinished branches; and a complete queue with no remaining currently justified actionable investigation. Any inconclusive item must state why additional available work is not expected to discriminate the claim or change a decision. A runnable, relevant pending experiment cannot be hidden under “diminishing returns.”

The independent reviewer examines that dossier and the underlying evidence, reruns missing material checks, and either endorses completion or states a concrete further investigation using the same actionable-entry fields. If it identifies such work, the campaign continues, with its results feeding a new closure decision. If no such work remains and all material verification/claims are closed or explicitly bounded, the reviewer signs completion. This is a documented judgment about the current evidence and available avenues, not proof of optimality, exhaustive search, or a guaranteed terminal time. Lead/reviewer disagreement is retained and investigated rather than resolved by an invented time quota.

External blockers, technical failures, user cancellation, and integrity stops are distinct from normal scientific completion. They preserve a stopped/incomplete outcome and the last verifiable artifact; they do not get relabeled “exhausted ideas.” The user can stop at any time. Changing the scientific objective or taking a newly consequential external action still requires authorization; open-ended duration does not expand task scope.

Record continuous campaign elapsed time, queue delay, lead/worker/reviewer activity, retries, process CPU time, and total available usage from start through closure. Parallel role time/resource sums can exceed campaign elapsed time. No costs disappear because a process fails, waits, or restarts. Technical watchdogs detect a stalled transport, nonresponsive child, resource violation, or broken integrity condition. Their conditions and recovery actions must be explicit and frozen; they are not hidden time limits on useful research. A watchdog timeout creates a technical event and diagnosis, not automatic scientific completion.

Final assessment is researcher-controlled automated evaluation with no LLM decision-maker. Its work is fixed by the frozen evaluation plan; ordinary process-health/resource controls prevent an indefinitely stuck evaluator without imposing a reviewer research quota. Record its elapsed time/resources separately and in the whole-study total. No price or total-duration guarantee follows from the no-cap design.

## 8. Enforced scheduling and score-independent measurement recovery

### One execution lane with usable shell access

One owner-controlled scheduler admits every arbitrary participant shell command and official native build, test, profile, memory-check, or benchmark operation. The same scheduler governs the automatic original-seed development comparisons and final native assessment. The participant's builtin unscheduled shell routes are disabled; a mediated command/exec route preserves the existing workspace sandbox, writable roots, network restrictions, technical process limits, and recorded command evidence. It supports ordinary shell syntax, local compilers, scripts, repeated experiments, and repairs. No one-shot command restriction or command-text classifier decides that an arbitrary shell command is harmless enough to bypass scheduling.

Acquire the execution lease before starting the process and retain it until the supported supervisor has established cleanup of the tracked process tree. An RPC acknowledgement, a root-process exit, a termination request, or silence on stdout alone does not establish descendant cleanup. Jobs already waiting at coordinator admission remain queued in FIFO order. Existing metadata locks can affect when a request reaches that queue; FIFO is not asserted for wall-clock arrival of all tool requests. A retry releases its old operation and rejoins the queue; it cannot monopolize the lane. Record queue admission, execution, cleanup, release, and cancellation events with their identities and timestamps. Process tracking and sandbox restrictions are finite operational controls, not hostile-code containment or exclusive ownership of the host.

Bounded structured source, contract, and evidence reads remain available during a benchmark, as do model planning and concise messages. Source edits made through arbitrary shell use the execution lease. A structured read executes no shell code, rejects path escapes, symlinks and nonregular files, and has explicit work/output bounds and continuation information. It must not wait on a metadata lock held for a native operation. Larger evidence is retrieved explicitly in bounded pieces. These reads are outside scored invocation boundaries and are not by themselves a timing-invalidating competing command. The scheduler still cannot rule out unrelated host load; record that limitation.

### Immutable attempt series and first-valid selection

Expected research failures, including compile errors, failed tests, wrong results, regressions, unsupported hypotheses, reviewer requests, and failed profiling, remain evidence. Workers may repair their branches and make new immutable snapshots. They may not erase a failure or turn an unchanged invalid artifact into a favorable result by repetition.

An official benchmark request is a series of immutable attempts bound to one exact source tree, candidate binary, reference source and binary, fixtures, purpose/review plan, technical limits, calibration method, realized measurement procedure and frozen estimator. Every attempt has its own operation ID, raw outputs, timing status, resource observations, cleanup evidence, and link to the series and previous attempts. An invalid partial attempt contributes no scored samples to a later complete attempt. A recoverable retry repeats the entire comparison under the same frozen procedure; it cannot rebuild, repair, reselect a reference, alter the sample count, or change a threshold.

The controller may automatically repeat only a timing attempt independently attested as invalid for one of two causes: an observed competing study-command overlap, or a specifically identified external preemption/interruption with an owner observer/event record. Cleanup must be confirmed, all source/binary/fixture identities must still match, the campaign must remain active, and no semantic, memory, resource, or integrity failure may be hidden by the interruption classification. Participant assertions, generic exceptions, disappointing scores, and uncertain cleanup cannot authorize recovery. The reason and evidence must be recorded before the retry, independent of whether any provisional timing looked favorable.

The retained configuration field `infrastructure_automatic_retries: 0` describes generic infrastructure/session relaunches, which are not permitted. It is not a limit on the explicitly classified, immutable timing-attempt recovery described here; that policy is implemented and tested separately. The field is descriptive and is not consumed as a measurement-attempt counter.

The first complete valid attempt ends the request and supplies its observation regardless of the score. Within an immutable nomination plan, the first complete valid official comparison in append order remains the promotion decision sample under §6. A valid low score, lower-bound failure, per-family regression, or completed sample below the calibrated target remains a valid observation and never triggers an automatic repeat. A candidate hang, candidate resource-limit failure, failed correctness test, or definite memory error also cannot trigger this measurement-recovery route. Ordinary scientific follow-ups and repaired-source experiments remain possible, with explicit questions and retained earlier evidence; they do not reset the binding decision sample.

There is no arbitrary count of recoverable measurement attempts and no scientific time/token budget. The continuous clock and all observed usage include waiting, invalid attempts, cleanup, and recovery. If recovery remains impossible because the independently recorded condition persists, surface that condition and waiting state; do not fabricate completion or silently discard the request. Explicit user/owner cancellation always stops recovery. An identifiable unresolved process, broken source/evidence binding, unknown backend failure, failed model-routing check, or lost model/owner session is a distinct technical or integrity blocker, not permission to repeat until a result appears.

### Terminal blockers and interventions

Uncertain subprocess cleanup quarantines subsequent resource work until an authorized, evidenced resolution; absence of cleanup evidence is not a recoverable timing event. Suspected evaluator defects, immutable-file changes, hidden-data exposure, unverifiable source/evidence binding, and unexplained promotion state stop dependent measured work and retain the last verifiable artifact. These events do not establish participant intent or misconduct. Model-session or owner-process loss preserves an incomplete campaign and its partial usage. This protocol does not silently create replacement model sessions or campaigns; any later amendment is separately declared.

A recoverable invalid timing does not itself stop the investigation or revoke an otherwise valid promotion. A failed automatic trajectory remains distinct from the underlying promotion and hypothesis verdict. The controller completes its allowed same-artifact recovery before reporting a valid point or a genuine unresolved blocker. True noncompletion remains in the planned denominator with its reason.

No human optimization steering is planned during measured campaigns. A user can stop work at any time. Messages that change scientific questions, code, stopping criteria, or the environment are interventions and must be disclosed. Execution of this frozen scheduler, attestation-based recovery, record append, and verified promotion is planned orchestration. New consequential actions still require their own authorization.

## 9. Journal and evidence integrity

Workers and leads submit new factual records to a journal service; they do not edit the authoritative history directly. The service validates the record schema, attaches an ID, timestamp, role/session ID, source hash, artifact pointers, and parent record where relevant, then appends atomically to an append-only event log. Deterministic rendered views may be rebuilt from that log. Every role can retrieve the permitted history for its own campaign through explicit bounded views, with record IDs and continuation information.

The service, not the participant, appends official build/test/benchmark outcomes and reviewer decisions from authoritative records. A participant's narrative is labeled a claim until linked evidence supports it. Corrections are new entries referencing the original; no earlier claim or negative result disappears. Ordinary malformed append requests return validation errors and may be corrected. Such a rejected request is not, by itself, a global fatal journal-integrity failure. Unauthorized modification of the authoritative log is a different event and blocks dependent work.

Status returns a compact operational summary rather than the entire authoritative state or numeric usage ledger. Short summaries and handoffs are allowed to support lead context; the underlying journal and permitted evidence remain available through explicit bounded retrieval. Retrieval exposes truncation/continuation and source identities instead of silently omitting material evidence. Summaries identify omitted detail and evidence links, not fabricated measurements. Archive exportable prompts, messages, tool actions, and worker reports without private hidden reasoning or authentication material. Record unavailable runtime context instead of claiming a complete reproducible model transcript.

## 10. Independent immutable final evaluator

Freeze the evaluator, oracle, corpus generation/selection rules, workload weights, correctness/resource probes, native timing method, schedules, estimator, uncertainty procedure, allowed restart policy, and output schema before any v3 measured optimizer starts. Only the evaluator owner can execute or maintain it; measured lead, workers, and reviewers cannot edit it or read hidden fixtures. Implementation reuse does not establish correctness: setup controls must test the actual v3 path.

The final endpoint for a normally completed campaign is the last promoted exact source when the task-based completion dossier is accepted, or the original seed if none was promoted. A stopped campaign preserves the last verifiable promoted source with its noncompletion status; do not manufacture normal closure. Seal source/build hashes, stopping reason, compliance status, and evidence IDs. A compliant seed endpoint with no gains is a valid negative outcome. An incomplete or compromised campaign stays in the planned denominator with its status; do not quietly replace it. Do not select the best campaign or historical score as the primary endpoint.

All three planned campaign endpoints, including any explicitly stopped-state seals admitted by the owner procedure, must be present before the final evaluator executes candidate assessment or releases any held-out endpoint result. The final evaluator freshly builds or validates the exact seed and endpoint artifacts, runs independent final correctness/resource checks across both final strata, then measures fresh paired seed-versus-endpoint performance only for valid endpoints. A confirmed failure in either stratum invalidates that endpoint before timing; it cannot be reported as a valid improvement based only on the other stratum. The evaluator does not multiply development ratios or reuse old baseline times. Partial or failed timing is not converted into an improvement estimate. Do not substitute an earlier source after failure. If the stopped workflow cannot supply all required truthful seals, final assessment remains blocked.

A final assessment is an observation, not another optimization round. Its outcome cannot authorize repair, reselection, extra campaign time, modified thresholds, or a replacement campaign. Each benchmark request uses the same immutable, score-independent attempt-series recovery defined in §8. An independently attested recoverable timing interruption can cause an automatic same-artifact repeat inside the first assessment; completed valid comparisons cannot be repeated for a better result. Retain every invalid attempt and select the first valid comparison. Candidate hangs, resource/correctness failures, unknown infrastructure faults, integrity failures, cancellation, and unresolved cleanup do not authorize this repeat. A new output directory or fresh evaluator invocation cannot reset the cohort's assessment identity. An unrecoverable assessment interruption retains a terminal report and missing values; any later amended execution must remain separately labeled.

Report two separate six-family strata: same-distribution/new-seed transfer is the primary performance portfolio, and changed sizes/distributions form a separate secondary shift portfolio. Each uses thirty complete paired blocks, fifteen pairs in each arm order per family, and the same estimator and joint bootstrap specified in §6. Final evaluation has no promotion threshold: report all valid estimates, absolute times, family ratios, and descriptive uncertainty, including no gain or regression. Do not combine the twelve families into an unlabeled primary score. The finite corpus is not a production workload distribution, and equal family weights are a convention. The design team must not inspect held-out fixture data as part of this methodology review; this document does not authorize doing so.

The native order seed is 2026100301; archive the realized family/arm schedule as authoritative. Each family calibrates both arms and uses the larger repetition count for both; the target sample duration is 0.05 seconds and the repetition ceiling is 65,536. Calibration/warmup data do not enter scored estimates. A completed scored sample below target remains included and flagged; it does not trigger recalibration or an adaptive rerun. Enforce the shared lease for arbitrary study-owned shell and every native operation so they do not overlap official timing. Bounded structured reads and model planning remain available as specified in §8. Record host, toolchain, CPU allocation, competing load where observable, calibration, and warm/cold conditions. Diagnostic profiles use their own artifact hash and workload identity; reduced diagnostic cases may not represent full-workload bottlenecks.

Independent final data reduce that selection problem but do not establish broad generalization. Benchmark blocks describe measurement uncertainty conditional on fixed artifacts; they do not increase the count of campaigns.

Do not connect old absolute baseline times to later candidate times as if they were a paired comparison; never infer total growth by multiplying parent-relative ratios. Plot only observed points, with no assumed upward curve or extrapolated improvement. Record the additional benchmark overhead as part of campaign and whole-study resources.

Report all campaigns individually before any aggregate, every hypothesis outcome, all nominations/revisions, review requests and decisions, time to promotions, no-gain/failed/incomplete outcomes, per-family results, absolute timings, resource observations, and intervention/recovery events. Process outcomes additionally distinguish actual delegated tool cycles (with child role, command/evidence IDs, and returned findings), hypotheses with factual reports, reports independently reviewed, repeat investigations/follow-ups, retained negative outcomes, and unreviewed/incomplete checkpoints. A spawned worker or written claim alone does not count as an executed investigation or verified review. Counts describe what occurred; they are not quotas or measures of scientific quality by themselves.

Any aggregate is descriptive unless a later approved design supports stronger inference. A small set of campaigns remains a single-task case study, not a general efficacy or reliability estimate. Plot only actual recorded trajectories, with failed and incomplete work visible; do not draw assumed continued growth or imply that longer activity must improve performance. Testing and traces provide finite evidence, not proof of total correctness, race freedom, optimality, or security.

## 12. All-role accounting and launch readiness

Capture requested and provider-reported model/effort for every lead, measurement worker, implementation worker, reviewer, recovery context, and any model-backed orchestration. Preserve observed usage with its semantics. Distinguish cumulative counters from per-request usage; do not double count reasoning included in output or parallel role totals. Record missing fields as unavailable with reasons, not zero. If the provider does not expose immutable model snapshots or effective settings, state that limit.

The canonical usage ledger binds every raw event to campaign, role, session, turn/request identifier where available, model, timestamp, event identity, and whether its counters are cumulative or incremental. Retain input tokens, cache-read tokens, cache-write tokens, output tokens, reasoning tokens, their inclusion/subset relationships, and the authoritative final status wherever exposed. Deduplicate repeated cumulative events, reconcile final session totals with request records, and avoid counting a parent aggregate again alongside its children. Count interrupted/failed requests and recovery contexts. A field supplied as a placeholder/default is not evidence of an observed zero.

Apply prices per request and model only when request partitioning and the priced model/tier are actually known. Use current dated official input, cache-read/write where relevant, output, tier, and long-context-band rules; do not subtract cache tokens twice, separately bill reasoning already inside output, or apply one role's model rate to all roles. If only session totals or incomplete cache breakdowns are available, calculate explicit supported bounds/scenarios and disclose what prevents an exact value. Preserve the source URLs, retrieval date, currency, units, formulas, and coverage. Reconcile delivered ledger subtotals to role, campaign and checkpoint coordinates. Reconciliation of observed role counters does not establish complete provider or billing coverage. Record remote compaction usage gaps, interrupted-turn tails, unauthoritative cache-write defaults, unknown request partitioning/tier, and unavailable setup/review work explicitly. Where unobserved work is unbounded, an observed-token API-equivalent interval is not a finite upper bound on whole-run cost. Full telemetry preflight must exercise all selected role models/efforts and these aggregation paths before freeze.

Report observed tokens, available direct billed cost, and separately labeled API-equivalent scenarios using dated official pricing and explicit cache/tier/request-band assumptions. Count all completed and failed role calls. Capture compiler/test/benchmark/profile CPU time and wall time, plus overall campaign elapsed time; parallel sums can exceed elapsed time. Report setup, methodology review, harness repairs, launch preflight, final evaluation, and interpretation separately and in any available whole-project total. Unavailable setup/review cost prevents a claim of complete whole-project cost.

No measured launch until user choices and exact config agree; execution access is verified without reading credentials; full role routing/no fallback and actual usage coverage are validated through an authorized telemetry preflight; task/seed/evaluator/source boundaries are hashed; completion, watchdog, and recovery rules are executable; reviewer reruns and journal mediation work; endpoints/embargo/accounting controls pass; and a dated immutable freeze manifest is recorded. A prepared draft, a passing unit test, or a selected role map is not itself evidence that a measured experiment ran.


## 13. New preflight and launch gate

A new v3 setup run must exercise the actual deployed role routing and tools, scheduler, cleanup supervision, and owner/evaluator interfaces. No historical readiness record, prior passing control count, or earlier measured outcome is imported as proof of v3 readiness. Setup records are labeled and excluded from measured campaign results. Keep failed, passed, pending, and not-run controls distinct.

Before freeze, require evidence for all of the following:

1. The pinned runtime really removes unscheduled builtin shell routes while the mediated arbitrary shell route remains usable with the same sandbox, working directory, writable roots, network policy, and technical limits. Exercise commands, scripts, local compilation, repeated repair, and normal shell syntax without loosening access.
2. Lead, worker, reviewer, automatic development trajectory, and final-evaluator native jobs use the same scheduler path. Exercise concurrent requests, FIFO admission, cancellation while queued and after admission, and absence of lock inversion.
3. A bounded source/evidence read completes while a real benchmark owns the lane, without acquiring its native/metadata lock. Compact status excludes whole-ledger usage dumps. Test path escape, symlink, nonregular-file, oversized-output and continuation behavior, and truthful access limits.
4. Real background and detached descendants, command timeout/cancel, lost response and disconnect controls establish the cleanup or quarantine path. No lease is released merely on an acknowledgement or root-command exit. Record the supported process-tracking limitation.
5. An independently injected external timing interruption or contamination retains its immutable invalid attempt and automatically repeats the exact source/binary/reference/fixtures through the actual development request and final evaluator path. Verify linked identities and requeue fairness. Accept the first valid observation even when it fails the improvement screen.
6. Candidate hangs, resource violations, semantic/memory errors, unknown exceptions, explicit cancellation, valid unfavorable scores, and valid under-target samples do not trigger automatic measurement retry. An overlap must not conceal a candidate failure.
7. Actual baseline build/test/profile/benchmark, intentional compile failure followed by a new repaired snapshot, a worker follow-up, no-change hypothesis and independent review, corrected journal request, immutable nomination, no-change rejection, and reviewer-endorsed closure run through the real multiagent interface. The setup task must not optimize the seed or disclose earlier optimization results.
8. Source/binary/fixture binding, append-only evidence, promotion/rollback consistency, required reviewer reruns, all-endpoint assessment embargo, stopped-state sealing, and first-assessment identity pass. Exercise final assessment on setup artifacts without releasing hidden measured fixture data to participants.
9. Full-path A/A and wrong-result/input-mutating controls, technical resource rejection, all configured memory/profile families, both final correctness strata, paired schedule, calibration, estimator, and raw-data retention pass under the actual v3 implementation. Reduced diagnostics retain their stated coverage limit.
10. Requested and observed model/effort routing, fallback prohibition, observed usage semantics, role aggregation, cache/default provenance, known missing provider coverage, and separate setup costs are recorded. Missing fields remain unavailable rather than zero.

An independent review must reconcile these records with the actual implementation, exact tool schemas and latest file hashes. Then the owner records a new immutable readiness/freeze binding the protocol, prompts, config, original seed, harness, evaluator, dependencies and setup evidence. Only that validated freeze permits the three new serial campaigns. The launcher must reject stale or changed bindings. After freeze no protocol, tool, evaluator, source treatment, or recovery-policy edit is silently applied to a measured campaign.

This protocol and its draft history contain no v3 outcomes. Passing a setup control would establish that control's observed behavior, not guarantee improvement, task completion, isolation, or full accounting in the future measured cohort.
